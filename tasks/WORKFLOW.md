# 작업 순서와 프롬프트

Claude Code와 Antigravity에게 각각 무엇을 시킬지, 어떤 순서로 붙여넣을지.

## 역할 분담

| 누가 | 무엇을 | 왜 |
|---|---|---|
| **Claude Code** | T01, T03~T07, 그리고 **모든 병합과 검증** | 여러 파일을 동시에 건드리는 일. 저장소 전체 맥락이 필요하다 |
| **Antigravity** | T02 애셋 10종만 | 파일 하나씩 독립적이고 종료 조건이 기계로 판정된다. 자율 반복에 맞다 |
| **사람** | 애셋이 **한 세트로 보이는지** 눈으로 판정 | 린터는 규칙 위반은 잡지만 "따로 논다"는 못 잡는다 |

> **두 도구를 같은 폴더에 동시에 붙이지 말 것.** 파일 워처가 서로의 저장을 덮어쓴다.
> 시간을 나누거나(권장) git 브랜치를 나눈다. T01과 T02는 건드리는 파일이 겹치지 않지만
> (`src/sim/` vs `src/assets/`) 동시 실행은 피하는 편이 안전하다.

## 단계 0 — 저장소 확인 · Claude Code

첫 판에는 코드를 고치지 못하게 막는다. 기준선을 먼저 확인해야 나중에 무엇이 깨졌는지 안다.

```
banana-lab 저장소에서 작업한다. 먼저 AGENTS.md 와 CLAUDE.md 를 읽어라.

시작 전에 아래 셋을 실제로 실행해서 확인해라.

1. npm install
2. npm run check
   - 테스트 29개 통과, 아트 디렉션 린터 "위반 없음" 이 나와야 한다
3. npm run dev 로 하네스를 띄우고 브라우저에서 확인
   - 왼쪽 바나나가 보이고, 익은 정도 슬라이더를 움직이면 색과 반점이 바뀌는가
   - 오른쪽 시야가 보이고, 방울 수를 1로 내리면 시야 안에 경계가 생기는가

셋 다 확인되면 저장소 구조를 3~4줄로 요약하고,
tasks/T01-state-machine.md 를 읽고 무엇을 할 계획인지 알려 달라.

이번 턴에는 코드를 고치지 마라. 확인과 계획만 한다.
```

```
tasks/T01-state-machine.md 를 수행한다.

작업 전에 반드시 읽어라.

  막고 싶은 상황이 나오면 막지 말고, 상태를 바꾼 뒤 무슨 일이 일어났는지 message 로 말해라.
- src/sim/ 안에서 document, window, Date.now(), Math.random() 을 쓰지 마라.
- reduce 안에서 원본 상태를 변형하지 마라.

카드의 합격 기준 6개를 하나씩 대조하면서 진행해라.
끝나면 npm run test 를 실제로 실행해 출력을 보여 주고,
"T01: ..." 형식의 한국어 커밋 메시지로 커밋해라.
```

**확인할 것** — 끝났다고 하면 `npm run test`를 본인이 한 번 더 돌린다.
특히 「하드 게이트는 두 종류뿐이다」 테스트. 이 프로젝트의 설계가 살아 있는지를 보는
유일한 자동 검사다.

## 단계 2 — T02 애셋 · Antigravity

10종을 한꺼번에 맡기지 않는다. 성격별 4그룹으로 나누고, **그룹 안에서는 순서대로** 만들게 한다.
받침 유리와 덮개 유리를 다른 에이전트가 만들면 유리 색조가 미묘하게 어긋난다.

| 그룹 | 애셋 | 왜 묶나 |
|---|---|---|
| A · 유리 | `slide, coverslip` | 같은 유리 색과 반사 처리를 공유한다 |
| B · 손도구 | `dropper, forceps, bottle` | 학생이 집어 드는 물건. 크기 감각을 맞춰야 한다 |
| C · 현미경 | `microscope` | 혼자서도 크다. 부품 16개 |
| D · 배경 | `dish, waste, tissue, bench` | 조작 대상이 아니라 단순하다 |

프롬프트는 `tasks/T02-PROMPT.md` 참조. `<그룹>` 자리에 위 표의 애셋 이름을 순서대로 넣는다.

**가장 흔한 오염원**: `src/render/fov.js` 를 읽히는 것.
시야 렌더러는 아트 디렉션 예외 구역이라 `rgba()` 와 `<filter>` 를 쓴다.
이걸 본 에이전트는 "여기선 되네" 하고 애셋에도 따라 쓴다.

## 단계 3 — 병합과 검증 · Claude Code

Antigravity의 보고를 믿지 않는다. 명령을 직접 실행해서 확인한다.

```
Antigravity 가 만든 애셋 10종이 src/assets/ 에 들어왔다. 병합하고 검증한다.

1. 각 애셋을 개별 검사한다. 보고를 믿지 말고 직접 실행해라.

   for a in slide coverslip dropper forceps bottle microscope dish waste tissue bench; do
     echo "=== $a ==="; npm run check:art -- $a
   done

   실패하는 것이 있으면 docs/01-art-direction.md 기준으로 네가 직접 고쳐라.
   고칠 때도 팔레트에 색을 추가하지 마라.

2. src/assets/index.js 의 ASSETS 에 10종을 등록하고 PENDING 배열을 비운다.

3. 각 애셋의 대표 상태를 SAMPLE_STATES 에 넣는다.
   Antigravity 가 보고한 값이 있으면 쓰고, 없으면 contract.js 의 states 를 보고 3~4개 만든다.

4. npm run check 로 전체 통과를 확인한다.

5. index.html 하네스에 "애셋 시트" 섹션을 추가해서 12종을 한 화면에 늘어놓아라.
   각 칸에 애셋 이름을 함께 표시한다.
   그다음 npm run shot 으로 라이트 모드와 다크 모드 스크린샷을 찍어 보여 달라.

6. 스크린샷을 네가 직접 보고 아래를 판정해라. 통과라고 쓰지 말고 근거를 대라.
   - 12종의 선 두께가 눈으로 같아 보이는가
   - 음영이 전부 우하단에 있는가
   - 받침 유리와 덮개 유리의 색이 같은가
   - 손도구 3종(스포이트·핀셋·시약병)의 크기 감각이 서로 맞는가
   어긋난 것이 있으면 어느 애셋의 무엇이 문제인지 짚어 달라.

커밋 메시지는 "T02: 애셋 10종 추가" 로 한다.
```

**사람이 볼 것** — 5번에서 나온 스크린샷 두 장을 직접 본다.
린터는 "규칙을 어겼는가"만 안다. **"한 세트로 보이는가"는 사람만 판정할 수 있다.**

## 믿지 말고 확인할 것

에이전트가 "완료했습니다"라고 할 때 실제로는 안 된 경우가 있다. 매번 이 셋을 직접 돌린다.

```bash
npm run check          # 테스트 + 린터. 종료 코드 0 이어야 한다
npm run dev            # 브라우저에서 실제로 열어 본다
git diff --stat        # 건드리지 말라고 한 파일을 건드렸는지 본다
```

| 증상 | 원인 | 대처 |
|---|---|---|
| 테스트는 통과하는데 화면이 이상하다 | 렌더러는 안 고치고 상태만 고쳤다 | `npm run shot` 으로 그림을 보게 한다 |
| 린터가 갑자기 통과한다 | 팔레트에 색을 몰래 추가했다 | `git diff src/style/tokens.js` |
| 「하드 게이트는 두 종류뿐」 실패 | 조작을 막는 코드를 넣었다 | 되돌리고 AGENTS.md §2.1 을 다시 읽힌다 |
| 애셋이 따로 논다 | 병렬 에이전트가 서로 안 봤다 | 어긋난 것만 골라 다시 시킨다 |
| 시야가 예뻐졌다 | 광학 상수를 바꿨다 | `npm run test` 가 잡는다. 되돌린다 |
